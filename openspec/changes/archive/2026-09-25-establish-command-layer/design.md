## Context

See proposal.md - Why/What Changes for motivation and scope. Relevant current-state facts that shape this design:

- `jobs/handlers.py` already has the right shape for a command: `run_backup_full(cluster, params, on_progress) -> dict`, `run_backup_incremental(...)`, `run_restore(...)`, `run_prune(...)` — no HTTP, no `print`/`sys.exit`, just orchestration over `planner`/`executor`/`restore`/`prune`/`health`/`repository`/`labels`/`concurrency`. `jobs/thread_backend.py::_run_job` calls `JOB_HANDLERS[job_type](cluster, params, on_progress)` inside a `try/except Exception`, and on failure does `job.error_message = str(e)` — it does not inspect exception type, so **any exception type is safe to raise from a command** as long as `str(e)` matches today's message text.
- `cli.py`'s `backup_incremental`/`backup_full`/`restore_command`/`prune_command` duplicate that same orchestration inline, but resolve the `Cluster` from a YAML config (`resolve_cluster`, upsert-on-`init`) instead of loading it from a DB row, and layer CLI-only concerns on top: `click.confirm`, `sys.exit`, `logger.*` calls, and `_handle_snapshot_exists_error`'s specific retry-command guidance (which needs `error_details["snapshot_name"]`, `label`, `config`, `repository`, `backup_type`, `group`, `baseline_backup` — all already available to the CLI adapter).
- `executor.execute_backup` currently returns `{"success": False, "error_message": ..., "error_details": {"error_type": "snapshot_exists", "snapshot_name": ...} | None}` instead of raising. Both `cli.py` and `jobs/handlers.py` currently branch on this dict; `handlers.py` collapses it to `raise RuntimeError(result["error_message"])`, **losing** `error_details` — which is exactly why `cli.py` couldn't be pointed at `handlers.py` as-is today.
- `api/routes/clusters.py::delete_cluster`, `repositories.py::create_repository`/`delete_repository`, and `schedules.py::run_due`/`_compute_next_run_at` currently do domain checks (active-job/enabled-schedule guard, StarRocks "already exist" string-sniffing, snapshot-retention guard, cron parsing) inline and raise `HTTPException` directly as the only expression of the outcome. `inventory_groups.py` (domain module) + `api/routes/inventory_groups.py` (thin translator raising `HTTPException` from `inventory_groups.InventoryMembershipConflictError`/`InventoryGroupNotFoundError`) is the existing in-repo template for how these should look instead.
- `jobs/backend.py` exposes a `JobBackend` registry keyed by name (`ThreadBackend.name = "thread"`); `submit_job` (`api/routes/jobs.py`) and `schedules.py::run_due` both call `registry.get(backend_name).enqueue(job.id)`, which is unaffected by this change — only the handler functions the backend calls are moving.

## Goals / Non-Goals

**Goals:**
- One implementation per use case (`backup_full`, `backup_incremental`, `restore`, `prune`, cluster deletion, repository create/delete, schedule run-due), reachable from `cli.py`, from the FastAPI routes, and from tests, with no HTTP or CLI concept inside it.
- Every business outcome a command can produce is representable as a domain exception (`exceptions.StarRocksBRError` subclass) carrying whatever structured data an adapter needs (e.g. `snapshot_name`), not just a message string.
- Zero behavioral drift: identical CLI stdout/stderr/exit codes, identical HTTP status codes/response bodies/`job.error_message` contents, verified by keeping the existing test fixtures' expected values unchanged while re-pointing what they invoke.

**Non-Goals:**
- Changing `cli_api/*` (out of scope per proposal.md).
- Introducing a request/response DTO layer, a CQRS-style command bus, or any framework for the command layer — these are plain functions in `commands/`, matching the project's existing flat-module style (`planner.py`, `executor.py`, `restore.py`, ...).
- Changing job backend selection, the `JobBackend` protocol, or how jobs are enqueued/polled.
- Adding new inventory-group validation patterns — `inventory_groups.py` already fits the target shape and is left alone except where a route directly calls it in a way this change touches incidentally.

## Decisions

### 1. `commands/` is `jobs/handlers.py` promoted and extended, not a new parallel layer
Move `run_backup_full`, `run_backup_incremental`, `run_restore`, `run_prune` from `src/starrocks_br/jobs/handlers.py` into `src/starrocks_br/commands/backup.py` / `restore.py` / `prune.py` (splitting by use case, matching the one-concern-per-module convention already used at the top level), keeping their exact signature shape `(cluster_or_session_args...) -> dict` / raises domain exception. `jobs/handlers.py` becomes a thin re-export (`JOB_HANDLERS` dict) importing from `commands/`, so `jobs/thread_backend.py` and `jobs/backend.py` need no changes beyond the import. Add `commands/clusters.py` (`delete_cluster`), `commands/repositories.py` (`create_repository`, `delete_repository`), and `commands/schedules.py` (`run_due_schedules`) for the logic being pulled out of routes.

Alternative considered: keep everything under `jobs/` and rename the module. Rejected — `jobs/` is scoped conceptually to the async job subsystem (backends, polling, progress), and `delete_cluster`/`create_repository`/`run_due_schedules` aren't jobs (they run synchronously, inline in the HTTP request). A dedicated `commands/` package makes the "this is the one place application operations live" boundary explicit, matching what the proposal's goal diagram asks for.

### 2. Backup failure detail becomes a domain exception, not a result dict — translated at the `commands/backup.py` boundary only
Add `exceptions.SnapshotAlreadyExistsError(StarRocksBRError)` with `snapshot_name` and (optionally) `label` attributes, and a `__str__` that reproduces today's `error_message` text exactly (`f"Snapshot '{snapshot_name}' already exists in repository"`, matching `executor.submit_backup_command`'s current string). `executor.execute_backup` itself is **left unchanged** — it keeps returning `{"success": False, "error_message": ..., "error_details": ...}` exactly as today, since 39 assertions across ~15 tests in `tests/test_executor.py` pin that dict contract and rewriting them carries risk disproportionate to this change's goal. Instead, `commands/backup.py`'s `run_backup_full`/`run_backup_incremental` — which already inspect `result["success"]` — become the translation boundary: they raise `SnapshotAlreadyExistsError` (when `error_details["error_type"] == "snapshot_exists"`) or a generic `BackupExecutionError(StarRocksBRError)` (otherwise, preserving `result["error_message"]` as the exception's string) instead of returning the dict or raising a bare `RuntimeError`. `cli.py`'s backup commands catch `SnapshotAlreadyExistsError` to call `_handle_snapshot_exists_error` with the same guidance text as today; `jobs/thread_backend.py` needs no change since it already does generic `except Exception as e: job.error_message = str(e)`.

Alternative considered: keep `execute_backup`'s dict-based return and have `cli.py` call the command but inspect the returned dict for `error_details`. Rejected — that still leaks a not-quite-domain-exception convention into the shared command's public contract and keeps two different error-signaling styles (exceptions everywhere else in the codebase, a dict here) for the same layer. Also considered changing `execute_backup` itself to raise; rejected per above (confirmed with user) as disproportionate blast radius on a heavily-pinned core function for no additional benefit — `commands/backup.py` is already the right translation boundary since it's the first caller both adapters share.

### 3. New domain exceptions for the routes being pulled apart, following the `inventory_groups.py` pattern exactly
Add to `exceptions.py`:
- `ClusterHasActiveJobError(cluster_id, ...)` / `ClusterHasEnabledScheduleError(cluster_id, ...)` — for `commands/clusters.py::delete_cluster`.
- `RepositoryAlreadyExistsError(name)` / `RepositoryStillHasSnapshotsError(name)` — for `commands/repositories.py`. `create_repository` keeps the "already exist" string-sniffing (it's translating a live StarRocks error, not a locally-checkable precondition — this is genuine domain logic that belongs in the command, just now raising instead of raising `HTTPException` inline) and raises `RepositoryAlreadyExistsError` instead of `HTTPException`.
- `InvalidCadenceError(cadence, reason)` — for `commands/schedules.py::run_due_schedules`'s (and a shared `_compute_next_run_at` helper's) cadence validation, reused by `create_schedule`/`update_schedule` in the route (those two stay as route-level validation calls into the same helper, since creating/updating a schedule is otherwise pure CRUD with no other business rule attached — see Open Questions).

Each API route catches its command's specific exceptions and maps them to the exact `HTTPException(status_code=..., detail=...)` it raises today — the message text in `detail=` is preserved verbatim so response bodies are unchanged.

### 4. `run_due_schedules` becomes one command call, still transactional in the same session
`commands/schedules.py::run_due_schedules(session, now)` contains the full loop from today's `run_due` route (query due schedules, conditional `UPDATE ... WHERE next_run_at == previously_due_at` per schedule, call `submit_job`, collect `triggered_job_ids`) and returns `(triggered_job_ids, triggered_count)` (or a small dataclass). `submit_job` (currently in `api/routes/jobs.py`) moves to `commands/jobs.py` alongside it, since `schedules.py` already imports it from `jobs.py` today and it's already framework-free except for one `raise HTTPException` on an unknown backend — that becomes `exceptions.UnknownBackendError` (promoting `jobs/backend.py`'s existing `UnknownBackendError` if it's already a plain exception, or aligning it to `StarRocksBRError` if not — check at implementation time) caught by the route.

The route keeps the `Session` dependency injection and passes `db` straight through, since `run_due_schedules` takes a `Session` (not a FastAPI `Depends`) — this keeps the command directly callable from a test or a future non-HTTP scheduler trigger without constructing a request.

### 5. Test re-pointing strategy
- `tests/test_jobs_handlers.py` moves to `tests/test_commands_backup.py` / `test_commands_restore.py` / `test_commands_prune.py` (or stays as one file if that matches current organization better — decide at implementation time based on current file size/content), calling `commands.*` functions directly with a fake `Cluster` row, exactly as it does today against `jobs.handlers`.
- `tests/test_cli_backup.py`, `test_cli_restore.py`, `test_prune_cli.py` keep their `CliRunner` invocations but stop asserting on deep orchestration details already covered by the new command-level tests (e.g. exact `execute_backup` call args) and instead assert CLI-adapter concerns: config/YAML parsing, `sys.exit` codes, `_handle_snapshot_exists_error` output text, confirmation prompts. Any orchestration assertion that has a command-level equivalent is deleted, not duplicated.
- `tests/test_api_clusters.py`, `test_api_repositories.py`, `test_api_schedules.py` keep HTTP-level assertions (status code, response JSON, auth) for the endpoints, but the deeper "does the guard logic work in every combination" cases move to new `tests/test_commands_clusters.py` / `test_commands_repositories.py` / `test_commands_schedules.py` calling the commands with a real/fake `Session`.
- `tests/test_api_cli_parity.py` is deleted (proposal.md).

## Risks / Trade-offs

- [Risk] Changing `execute_backup`'s failure signaling from dict to exception could silently change behavior if some caller relies on the dict shape rather than the exception. → Mitigation: grep all callers of `executor.execute_backup` and `executor.submit_backup_command` before changing the contract; `submit_backup_command` itself can keep returning a tuple internally (it's a lower-level helper used inside `execute_backup`) — only `execute_backup`'s outward contract (used by `cli.py` and `commands/backup.py`) needs to change to raising.
- [Risk] Preserving exact message text in new domain exceptions' `__str__` by hand is easy to get subtly wrong (e.g. a trailing period or different quoting), which would change `job.error_message` in the API and CLI stderr text, a silent behavior change this proposal explicitly disclaims. → Mitigation: write the new exception's expected string first from the current source (`executor.py`, `clusters.py`, `repositories.py`, `schedules.py` literals), assert it in a unit test, then wire the exception in — don't wire first and eyeball after.
- [Risk] Splitting `run_backup_full`/`run_backup_incremental`/`run_restore`/`run_prune` across new `commands/*.py` modules while `JOB_HANDLERS` in `jobs/handlers.py` needs to keep re-exporting all four under the same string keys — an incomplete re-export breaks job dispatch silently until a job of that type is submitted. → Mitigation: keep `JOB_HANDLERS` construction and its keys in one place (`jobs/handlers.py`) and cover it with a test asserting all four keys resolve to the expected `commands.*` callables.
- [Trade-off] `commands/clusters.py::delete_cluster` and `commands/repositories.py` still take a raw SQLAlchemy `Session`, so the command layer isn't fully persistence-agnostic — consistent with how `inventory_groups.py` and `jobs/handlers.py` already work in this codebase, so this isn't a new pattern, just applying the existing one more widely.

## Migration Plan

1. Add new domain exceptions to `exceptions.py` (with string-match tests) before touching any call site — no behavior change yet, purely additive.
2. Introduce `commands/` package: move backup/restore/prune handlers first (mechanical relocation + import fix in `jobs/handlers.py`, `jobs/thread_backend.py` untouched), run the full test suite (should be green with only import-path test updates).
3. Change `executor.execute_backup`'s failure path to raise the new exceptions; update `commands/backup.py` and `cli.py`'s except-clauses together in the same commit so there's no window where the contract mismatches.
4. Rewrite `cli.py`'s backup/restore/prune command bodies to call `commands/*` instead of the inline sequence; delete the now-redundant inline orchestration and its now-passing duplicate assertions in `test_cli_*`.
5. Extract `commands/clusters.py`, `commands/repositories.py`, `commands/schedules.py` (+ `commands/jobs.py::submit_job`) from their routes one at a time, each as its own commit: move logic, add exception translation in the route, re-point tests.
6. Delete `tests/test_api_cli_parity.py` once step 4 lands and the property it checked is structural.
7. No production data migration, no schema change, no deployment ordering constraint — this is a same-process code reorganization; rollback is a plain revert of the relevant commit(s).

## Open Questions

- Whether `create_schedule`/`update_schedule`'s cadence validation should also move fully into a `commands/schedules.py` function (e.g. `validate_cadence`) shared with `run_due_schedules`, or stay as route-level calls into a shared helper — doesn't change the spec, approach, or task breakdown either way; decide at implementation time based on which reads cleaner once the code is in front of you.

## Amendments Found During Implementation

### A1. `execute_backup`'s dict contract is translated only inside `commands/backup.py`, not inside `executor.py` itself
Superseded Decision 2's literal wording ("`executor.execute_backup`'s failure path" raising) - see the updated Decision 2 text above. `executor.py` and `tests/test_executor.py` (39 assertions pinning the dict contract) are untouched; `commands/backup.py::run_backup_full`/`run_backup_incremental` are the only translation point, since they already inspect `result["success"]`. Confirmed with user before implementing (avoided a disproportionate rewrite of a heavily-pinned core function for no behavioral benefit).

### A2. `cli.py`'s per-step backup narration is sourced from the command via `on_progress`, not re-computed by the CLI adapter
Implementation revealed that `cli.py`'s current `backup_incremental` prints two messages ("Using specified baseline backup: X" / "Using latest full backup as baseline: X (type)") that depend on data only available *during* orchestration - specifically, whether the incremental backup's baseline was user-specified or resolved via `planner.find_latest_full_backup`. Fully delegating orchestration to `commands.backup.run_backup_incremental` means `cli.py` no longer computes this data itself, and CLI adapter code re-running that lookup separately (purely for display) would mean either running the real StarRocks connection/health-check/lookup sequence twice, or - worse - re-running mutating steps like `concurrency.reserve_job_slot` twice, which breaks concurrency control and duplicates job-slot reservations.

Resolution: `run_backup_incremental` invokes the (already-existing) `on_progress` callback once, early, with a small event dict (`{"event": "baseline_specified", "baseline_backup": ...}` or `{"event": "baseline_resolved", "latest_backup": {...} | None}`) at the point it resolves the baseline - the same callback parameter already used for `execute_backup`'s poll-progress updates, just invoked once more before polling starts. `cli.py`'s adapter passes an `on_progress` callback that pattern-matches on `event` and prints the exact same message text as today. This is the only place command output is sourced from a callback rather than the return value; every other cli.py message (health/repo/label/partition-count/job-slot/success/failure) either isn't asserted by any test and is dropped, or is derived directly from the command's return value or a caught exception's message text (see task 4.1-4.2 notes for the exact mapping). This is a net improvement in CLI/API parity (the job/API path now also determines the same baseline info via the same code path, where before it never called `find_latest_full_backup` at all) with no observable behavior change to either adapter.

### A3. `commands/restore.py::run_restore` takes `skip_confirmation` as a parameter instead of hardcoding `True`
`cli.py`'s `restore` command's `--yes` flag currently flows into `restore.execute_restore_flow(..., skip_confirmation=yes)`, which gates a raw `input()` confirmation prompt inside the pre-existing `restore.py` domain module (out of scope for this change). Hardcoding `skip_confirmation=True` in the command (as `jobs/handlers.py` did) would silently drop this interactive prompt for the CLI. `run_restore(cluster, params, on_progress=None, *, skip_confirmation=True)` now takes it as a keyword param defaulting to `True` (preserving the job/API path's forced-skip behavior, since there's no interactive terminal to confirm against over HTTP); `cli.py` passes its own `--yes` flag value through.

### A4. Prune's per-snapshot failure policy: abort-on-first-failure (see proposal.md's disclosed behavior change)
Implementation revealed `cli.py`'s current `prune` continues attempting remaining snapshots after one delete fails, while `commands/prune.py::run_prune` (from `jobs/handlers.py`) aborts the batch on the first failure - a genuine pre-existing behavioral divergence between the two paths this consolidation forces a choice on. Per explicit user decision, the unified command aborts on first failure (matching the prior job/API behavior); `cli.py`'s prune adapter changes to match, and `tests/test_prune_cli.py::test_prune_partial_failure_continues_deletion` is rewritten to assert the new abort behavior. See proposal.md's "No CLI flag..." paragraph for the disclosed-change statement.

### A6. `commands/restore.py::run_restore` raises `NoTablesFoundError`/`RestoreExecutionError` instead of generic `RuntimeError`
Same category of fix as Decision 2/A1 for backup: `cli.py`'s restore command needs to distinguish "no tables found" (rich-formatted via `error_handler.handle_no_tables_found_error`) from a generic restore-flow failure (`logger.error(f"Restore failed: {e}")`) to preserve its existing output. `jobs/handlers.py`'s original `run_restore` used a single generic `RuntimeError` for both, which was fine for the API/job path (both just become `job.error_message`) but loses the distinction `cli.py` needs. `commands/restore.py::run_restore` now raises the existing `exceptions.NoTablesFoundError(group=group, label=target_label)` (identical parameters `cli.py` already passed to this exception directly) for the empty-tables case, and a new `exceptions.RestoreExecutionError(message)` for `execute_restore_flow`'s failure case. Both are `StarRocksBRError` subclasses with no HTTP/CLI concept, consistent with the rest of the command layer.

### A7. Shared `mock_resolved_cluster` test fixture needs to fake `decrypt_password` too
Discovered when `cli.py`'s adapters started calling `commands.*`, which connects via `commands._shared.connect(cluster)` - this decrypts `cluster.password_encrypted` for real. The existing `mock_resolved_cluster` fixture (used across `test_cli_backup.py`, `test_cli_restore.py`, `test_prune_cli.py`, `test_cli_exceptions.py`, etc.) returns a `Cluster` with a placeholder (non-Fernet) `password_encrypted` string, and never previously exercised real decryption because the old `cli.py` connected using `os.getenv("STARROCKS_PASSWORD")` directly, never reading `cluster.password_encrypted` back. This was always an implicit production requirement (`resolve_cluster` already calls the matching `encrypt_password` on every invocation), just untested. Fixed by adding `mocker.patch("starrocks_br.commands._shared.decrypt_password", return_value="test_password")` to the shared fixture in `conftest.py`, rather than repeating it per test file.

### A5. `cli.py`'s prune adapter calls `run_prune` twice (dry-run plan, then real execution) to preserve the confirm-before-delete UX
`cli.py`'s prune needs the concrete list of snapshots-to-delete *before* deciding whether to prompt for confirmation or honor `--dry-run` - but `commands/prune.py::run_prune` combines planning and execution in one call. Since planning (`get_successful_backups`, `verify_snapshot_exists`, `filter_snapshots_to_delete`) is read-only and safe to repeat, `cli.py` calls `run_prune(cluster, {**params, "dry_run": True})` first to get `would_delete`, prints/prompts based on that, then - unless the user's own `--dry-run` was set or they declined the prompt - calls `run_prune(cluster, {**params, "dry_run": False})` again to actually delete. This keeps the actual filtering/deletion algorithm in one place (`commands/prune.py`) while preserving the CLI's preview-then-confirm interaction, at the cost of one extra read-only planning pass when a real deletion proceeds.
